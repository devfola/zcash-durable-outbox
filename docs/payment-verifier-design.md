# Independent payment-effects verifier design

Status: **implemented and tested against actual saved PCZTs and extracted transactions**. See [verifier validation](../verifier/VALIDATION.md) and [18 real-fixture results](../integration/evidence/real-pczt-verifier/summary.json). The helper has no RPC or publication capability; its successful report is not itself a live-adapter qualification flag. The original two-action design below was expanded to two through eight actions after the real wallet produced four change outputs; the implementation and validation report are authoritative for the supported shape.

## Exact baseline and deliberately bounded profile

Use Zallet `e5c16c464d2d641e5a7c386f3682cfa37e1c43f9`, its wallet dependency revision `1f6bb2072e7fcb142b0d90ff7b267a8699a84818`, `pczt 0.9.3`, `zcash_primitives 0.30.1`, `zcash_keys 0.16.1`, `zcash_protocol 0.10.5`, and the locked `orchard 0.15.3`. Wallet packages patched in Zallet must resolve from the same git revision, not an independently selected latest crate. Retain the lockfile and source hashes with qualification results.

The implemented first profile is **regtest, NU6.3, V6, Ironwood-only, one recipient, one nonzero input, two through eight actions, with individually verified internal change outputs**. It uses `BranchId::Nu6_3` (`0x37a5165b`) and `TxVersion::V6`, with no NU7 build cfg or ZIP-233 feature. It permits no transparent, Sprout, Sapling, or old Orchard component. The actual deployment's regtest activation schedule is immutable configuration shared with Zebra and Zallet. The executed Zallet release is `987382f67e622915228686e9f956c6a9c9a7514c`; its relevant PCZT files match the source baseline below.

The eight-action ceiling bounds verification work and is not a claim about all Zallet proposals. The real default target is four change notes; every positive change output must independently pass the same internal-address, commitment, ciphertext and memo checks. Current `fund_source="orchard"` includes both old Orchard and Ironwood, so that RPC argument alone does not enforce the profile. Use a disposable account funded only in Ironwood and independently check the resulting PCZT. ZIP-317 uses the actual action count: the observed five-action transaction paid 25,000 zat.

## Bootstrap a trusted account binding

The verifier needs a trusted sender UFVK outside the transaction artifacts. Do this once while creating the disposable wallet, before accepting payment IDs:

1. Obtain the dedicated account UUID and one registered unified address with `z_getaccount(UUID)` or `z_listaccounts(true)`. `z_getaccount` returns `account_uuid`, optional `seedfp`/`zip32_account_index`, and `addresses`; account/address derivation metadata is not a substitute for the key.
2. Unlock the disposable wallet, then call `z_exportviewingkey(known_ua, false)`. For a UA this returns the account's encoded UFVK. It does **not** export spending authority. The implementation reads the stored UFVK, so this bootstrap trusts the newly provisioned disposable wallet, not a value received inside a later PCZT. For stronger bootstrap assurance, independently derive the UFVK from the synthetic seed under the configured network/account index and compare; never obtain a production seed.
3. Decode with `zcash_keys::keys::UnifiedFullViewingKey::decode(&local_network, encoded)`, require `ufvk.orchard().is_some()`, and independently derive/check the known funded UA receiver using the recorded diversifier index. `UnifiedFullViewingKey::address(index, request)` and `UnifiedAddress::orchard()` are public APIs. Restrict the registration UA to an Orchard receiver for this profile.
4. Persist the encoded UFVK/fingerprint, network, account UUID, known address/index, dependency pin, and activation configuration in immutable wallet configuration. Never replace it using PCZT signing hints, `user_address`, private proposal metadata, or a runtime wallet response. Treat it as private viewing material in logs/files.

Exact RPC implementations: [z_exportviewingkey](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/z_export_viewing_key.rs), [z_getaccount](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/get_account.rs), [account metadata](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/list_accounts.rs). Key/address APIs are in [zcash_keys::keys](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_keys/src/keys.rs) and [zcash_keys::address](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_keys/src/address.rs).

## Exact public API route to parsed PCZT information

`Pczt::parse(bytes)` parses the saved binary artifact. Several wire-level spend fields lack public getters. Do **not** mirror its private encoding or deserialize the backend's private `postcard` enum. Instead use:

`pczt::roles::verifier::Verifier::new(pczt.clone()).with_ironwood::<VerifierError, _>(|bundle: &orchard::pczt::Bundle| { ... })`.

The callback receives the fully parsed protocol bundle. Existing pinned end-to-end code demonstrates `bundle.actions()[i].spend().fvk()` and `.alpha()` through this API; other parsed note getters are exercised by the pinned parser/prover. The wire `pczt::orchard::Output` independently exposes `recipient()`, `value()`, `rseed()`, `cmx()`, `ephemeral_key()`, `enc_ciphertext()`, `out_ciphertext()`, and `user_address()`. `Pczt::resolve_fields()` reconstructs legitimately compacted fields, but does not establish that already-present metadata is truthful. Keep the original saved artifact unchanged and use clones for inspection.

The verifier callback is an access/validation mechanism; constructing it alone does not validate payment policy or the final proof. [Public Verifier callback](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/verifier/orchard.rs), [existing FVK extraction fixture code](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/tests/end_to_end.rs#L798), [field resolution](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/orchard.rs#L2037).

## Fail-closed assertions

All amounts below are checked integer zatoshis with bounded addition/subtraction. Missing note information is an error, never an implicit zero. Run policy checks on created/proven/signed artifacts and repeat the decisive cryptographic/effects checks against the final bytes before commitment.

| Area | Required assertion and concrete mechanism |
| --- | --- |
| Address/network | Decode the approved recipient with the real `zcash_keys::address::Address` API under the immutable regtest parameters. Require a UA with an Orchard receiver, then compare actual raw receiver bytes. Reject an address equal to the sender's permitted internal-change receiver, to keep payment/change classification unambiguous. Never compare only `user_address`. |
| Global transaction | Require PCZT `global().tx_version()` / `version_group_id()` to equal `zcash_protocol::constants::V6_TX_VERSION` / `V6_VERSION_GROUP_ID`, branch `Nu6_3`, nonzero approved expiry interval, and the agreed locktime policy (zero for this profile, verified on independently extracted final structure). No implicit future branch acceptance. |
| Excluded pools | PCZT transparent inputs/outputs and Sapling spends/outputs must all be empty; old Orchard actions must be empty, with no nonzero value sum. Final parsed transaction must have `transparent_bundle()`, `sprout_bundle()`, `sapling_bundle()`, and `orchard_bundle()` all `None`. Any discrepancy fails. |
| Allowed bundle | Require two through eight Ironwood actions and the expected `ironwood_v3()` bundle version/flags with spends, outputs, and cross-address enabled. Use the real bundle's `bundle_version()` and `flag_byte()`; reject other flag configurations. Require the actual nonempty anchor before extraction/final validation. |
| Real input | In the parsed callback require complete spend note components, positive `value()`, and `fvk().to_bytes()` equal to the pinned sender FVK. Call `spend.verify_nullifier(Some(sender))` and `spend.verify_rk(Some(sender))` without permissive missing-component exceptions. Require exactly one positive input. Reject every additional positive input, foreign FVK, missing field, or duplicate nullifier. |
| Padding input | Every other input must carry a complete valid zero-valued note whose nullifier, randomized key and action value commitment checks succeed. It may use a dummy FVK through the upstream dummy-note path. Missing value/FVK/recipient/rho/rseed cannot be accepted as padding. An action's dummy input does not make its paired output a dummy. |
| Recipient output | Recover the actual note and all memo bytes as described below. Require exactly one positive output to the approved receiver, with the exact approved amount. No aggregation, amount split, or second output to the same recipient is permitted. |
| Change | Every additional positive output must pay exactly `sender_fvk.address_at(0u32, orchard::keys::Scope::Internal)`. Derive this from the pinned key. Also decrypt each final action using the prepared internal IVK under `IronwoodDomain` and require identical note/value/memo. Require canonical no-memo bytes for change. Reject other wallet-owned external addresses and other internal diversifiers for this first profile. Multiple individually verified outputs support Zallet's default split change. |
| Zero outputs | Every remaining output must be recovered and commitment-checked with value exactly zero. An absent recipient/value or decryption failure is an error. Permit only fixed no-content dummy memo forms: all-zero bytes or canonical no-memo bytes. Do not skip ciphertext or an output solely because optional display metadata is absent. |
| Extra outputs | Classify **every** output by recovered value/receiver; any positive output not uniquely accounted for as the single payment or a verified internal change output is rejected. No blanket exemption for wallet metadata, `InternalShielded`, or unknown address fields. |
| Balance/fee | Independently compute input total minus all recovered output totals. It must equal the actual final bundle value balance and the final transaction's `fee_paid` result. Require exactly `zip317::FeeRule::standard().fee_required(...)` for the observed action count, and no more than the approved maximum. The actual five-action fixture pays 25,000 zat. Dust-added overpayment is rejected. |
| Expiry/tip | Parse and inspect actual `Transaction::expiry_height()`, require it in the immutable approved interval and strictly after the next candidate mining height. Recheck chain/network/branch/expiry before each submission; after expiry require reconciliation and never reconstruct a replacement. |
| Authorization | After proofs/signatures exist, require local independent extraction and actual final-bundle proof/signature validation to succeed. Do not accept `proof_complete`, signed-action counts, `stored`, or a wallet-supplied txid as cryptographic validation. |

The upstream Signer checks nullifiers but deliberately tolerates missing note fields; this verifier does not copy that tolerance. Its implemented calls supply the trusted sender FVK and also check randomized keys, action value commitments, output commitments and cross-address restrictions. Parsed input metadata is tied to the actual proof/public nullifier through those consistency checks and the verified final proof, rather than trusting its stated value. Any inability to establish this complete-note path for a fixture blocks that shape. [Signer checks](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/signer/mod.rs#L485).

The selected change address is concrete upstream behavior: the backend builds Ironwood change with `orchard_fvk.address_at(0u32, Scope::Internal)`. Prohibiting the old Orchard bundle avoids its post-NU6.3 same-address-change complications. [Backend change construction](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_backend/src/data_api/wallet.rs#L2428). ZIP-317 accepts a separate Ironwood action count in [fee_required](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_primitives/src/transaction/fees/zip317.rs#L180).

## Memo and output authenticity

The canonical intent must distinguish **no memo** from an empty-string memo. With the current API convention, `memo_hex=""` means no memo: omit the Zallet RPC `memo` field and expect `MemoBytes::empty()`, whose 512-byte encoding is `0xf6` followed by 511 zero bytes. A nonempty hex value is raw user memo data, decoded without text interpretation and padded on the right with zeroes using `MemoBytes::from_bytes`. For example `"00"` produces 512 zero bytes; it is different from no memo. Compare all 512 bytes with `as_array()` or `into_bytes()`. Never strip trailing zeroes, decode UTF-8, normalize text, or compare only `as_slice()`. [Canonical memo APIs](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/components/zcash_protocol/src/memo.rs#L85), [RPC memo parsing](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/payments.rs#L80).

On a clone, `Redactor::redact_ironwood_with` and each action's `replace_enc_ciphertext_with_decrypted_memo_plaintext(orchard::note::NoteVersion::V3)` can recover memo data. Read `EncCiphertext::MemoPlaintext(m).to_memo()` and reject ciphertext that remains encrypted. This must use **V3 for Ironwood**, not the V2 used for old Orchard.

For decisive validation against actual transaction bytes, reconstruct each output note from complete PCZT recipient/value/rseed and the paired action nullifier (`rho`), using `orchard::Note::from_parts(..., NoteVersion::V3)`. Require its extracted commitment to equal the final action's `cmx`. Use `zcash_note_encryption::try_output_recovery_with_pkd_esk` with the reconstructed note's domain-derived `pk_d`/`esk` and the **actual final action/ciphertext**, under `orchard::note_encryption::IronwoodDomain`; require recovery success and exact receiver/value/memo agreement. This handles a PCZT which already carries memo plaintext too: the decisive check still authenticates final ciphertext. Do not treat `EncCiphertext::MemoPlaintext` itself as proof.

For change, `PreparedIncomingViewingKey::new(&sender_fvk.to_ivk(Scope::Internal))` plus `try_note_decryption(&IronwoodDomain::for_action(action), &prepared_ivk, action)` authenticates that the final ciphertext belongs to the sender. The pinned backend's generic `NoteEncryptionDomain::<IronwoodVersion>` is the same domain route. [Domain-correct decrypt/recovery path](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_backend/src/decrypt.rs#L207), [public memo recovery API](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/redactor/orchard.rs#L225), [existing note reconstruction and authenticated recovery](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/orchard.rs#L350).

## Tie returned raw bytes to the saved signed PCZT

Do not compare only txids: they do not authenticate all authorization data, and V6 permits deferred anchors. Do not require literal equality with an independent extraction either: extraction creates randomized binding signatures.

1. Parse the actual returned raw bytes with `zcash_primitives::transaction::Transaction::read(&mut Cursor, BranchId::Nu6_3)`. Require complete consumption, the exact profile, and canonical serialization round-trip equality with the received byte vector. Compute `actual.txid()` locally and compare its canonical string with the wallet response. Reject extra bytes and all parse/round-trip discrepancies.
2. From a clone of the **durably saved signed PCZT**, create an in-memory expected transaction with `SpendFinalizer::new(...).finalize_spends()` then `TransactionExtractor::new(...).with_orchard(&verifying_key).extract()`. This is a local pure artifact operation with no wallet DB/RPC call; its output is never chosen, stored for broadcast, or submitted. The verifier key comes from the asserted `ironwood_v3()` bundle/circuit version. This verifies PCZT proofs and signatures locally.
3. Compare actual and expected typed transaction structure exhaustively: version, branch, locktime, expiry, absent prohibited bundles; Ironwood `bundle_version`, `flag_byte`, value balance, anchor, proof bytes, action count/order; each action's `cv_net`, nullifier, randomized validating key, note commitment, ephemeral key, encrypted note ciphertext, outgoing ciphertext, and spend-authorization signature. These public getters are exercised by Zallet's raw-transaction encoder. Compare locally computed txids too. The **only** excluded field is the bundle binding signature.
4. Validate the actual binding signature instead of ignoring it. Obtain the saved PCZT's shielded sighash using `pczt::roles::signer::Signer::new(saved_pczt.clone())?.shielded_sighash()`. Structural equality above establishes that actual effects/anchors/proof/spend signatures are the ones reviewed. Call `orchard::bundle::BatchValidator::new(&verifying_key)`, `add_bundle(actual_ironwood_bundle, sighash)`, and `validate(rand_core::OsRng)`, propagating every error/false result. This is the same concrete validation API used by the pinned extractor. Do not substitute the locally generated binding signature into bytes that may be committed or published.
5. Run complete payment/memo/change/fee checks against the actual final structure/ciphertexts. Require Zallet extraction `stored=true` for the wallet-created PCZT as an additional integration observation. Only then atomically commit the **actual returned byte vector**, SHA-256 integrity digest, independently computed real txid, and verification evidence. Publish only a new durable read of those actual bytes.

Exact APIs: [transaction parsing/getters/serialization](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_primitives/src/transaction/mod.rs), [typed final action getters](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/get_raw_transaction.rs#L766), [randomized extractor](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/tx_extractor/mod.rs), [actual batch validation](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/tx_extractor/orchard.rs), [saved-PCZT sighash](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/signer/mod.rs#L180).

This procedure does **not** solve a lost wallet extraction response. Locally extracted comparison bytes have a different randomized binding signature and are not proof of the wallet's recorded raw bytes. Preserve wallet ownership and reconcile that boundary separately; never use the verifier as a substitute final-byte recovery path. After a real final commitment, do not call any extractor again during retries.

## Could exact-spend/no-change avoid a viewing key?

A controlled fixture can fund one Ironwood note whose value is exactly the intended payment plus the standard two-action fee, then request that payment and require all other outputs to be authenticated zeroes. That removes positive-change classification, but not output/memo/proof verification or sender-input ownership. It still benefits from the pinned sender FVK and still requires complete dummy data.

It is unsuitable as the general payout profile: arbitrary business amounts rarely match a selected note minus the exact fee; Zallet RPC does not let the outbox nominate an arbitrary input set or set a change address; and preparing one exact note per payout moves construction/race concerns into a separate prefunding workflow. It is useful as an early live qualification fixture, not an unsafe workaround for change verification. Prefer the concrete pinned internal-address check once a real fixture confirms it.

## Executed validation and scope

The standalone helper compiled with the committed lockfile. Genuine created,
proven and signed five-action PCZTs passed effects-only checks, including the four
independently decrypted internal change notes. Both original and repeated Zallet
extractions passed completed authorization checks with one consensus txid and
different raw bytes. Thirteen negative cases reject altered intent policies,
expired artifacts, unsigned completed input, trailing raw bytes and a corrupted
actual binding signature. See [the precise executed cases](../verifier/VALIDATION.md);
this is not a claim that every possible malformed PCZT has been tested.

The helper remains bounded to its explicit profile and has no publication
capability. It does not authenticate the supplied tip, node activation schedule,
chain membership of inputs, or account bootstrap provenance. The live adapter
must check the qualified node configuration and retain uncertain wallet claims.
Lost responses, caller death, wallet restart and publication exclusion require
separate real-process qualification; a successful artifact report alone never
enables a live adapter.
