# Zallet PCZT wallet boundary qualification

Status: **real wallet-boundary experiments completed for the pinned regtest NU6.3 profile; service acceptance is reported separately**.

This report separates initial executable source inspection from subsequent funded local-chain observations. No production wallet, real funds, or external payment was used. Review date: 2026-10-20 (America/Toronto).

## Current Outbox correction and scope

The wallet observations below remain historical facts about their pinned wallet processes. The earlier nine service scenarios and unbound saved-CREATE supplement used the pre-correction Outbox binary; they do not qualify the new CREATE-origin check. Corrected local validation passed: **43 Rust tests (42 library + 1 CLI)**, formatting, strict Clippy with warnings denied, build, and **10 compiled HTTP/CLI smoke checks with zero remote calls**. [Correction results and hashes](../evidence/correction/summary.json). The corrected executable subsequently passed all nine scenarios plus genuine identical-intent A/B CREATE recovery on a fresh disposable stack with the actual verifier. [Corrected real-stack report](corrected-real-stack-acceptance.md). A missing origin binding was confirmed, but no on-chain loss was demonstrated.

The Outbox profile supports **exactly one positive Ironwood sender input**. Multiple positive inputs and other unsupported shapes can fail verification after CREATE; ordinary errors after invocation may also quarantine the entire dedicated wallet. Failure paths retain ownership/in-flight fences. Do not clear claims, retry under a new ID or attach a fresh Outbox database to escape quarantine.

Saved-CREATE recovery requires a durable operation ID bound before the CREATE RPC to payment ID, owner and canonical-intent digest, plus an exactly matching original `create-{operation_id}/binding.json`. Content/effect equality alone is insufficient when two IDs have identical details. Legacy unbound evidence stays quarantined. [Corrected contract](recovery.md), [current acceptance scope](acceptance-status.md).

## Operation and publication boundary

| Operation | Executed implementation path | Source assessment |
| --- | --- | --- |
| `pczt_create` | Builds request; selects inputs; creates a single-step PCZT; records proposal/signing metadata | No broadcast call. Inputs are **not reserved** for this PCZT. May consume address/change derivation state. Keep exclusive wallet construction ownership. |
| `pczt_inspect` | Parses the PCZT and returns metadata | No wallet write or publication path. Does not verify proofs, signatures, or claimed output metadata. |
| `pczt_prove` | Proves saved PCZT in `spawn_blocking` under `PROVING_SLOTS` | No wallet storage or publication path. Caller loss does not establish cancellation. |
| `pczt_sign` | Resolves seed/signing hints; signs saved PCZT; returns artifact | No transaction storage or publication path found. Signing can produce new authorization bytes; completed artifacts must be saved. |
| `pczt_extract` | Finalizes spends; verifies shielded authorization; extracts; stores wallet-created transaction; reads it back; returns `{hex,txid,stored}` | Wallet mutation occurs **before** response. No broadcast call in this path. |

The above conclusions follow the implementations in [PCZT create](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/pczt_create.rs), [inspect](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/pczt_inspect.rs), [prove](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/pczt_prove.rs), [sign](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/pczt_sign.rs), and [extract](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/pczt_extract.rs). They are source assessments; subsequent funded observations are recorded below.

`z_sendmany`, `z_sendfromaccount`, and `z_shieldcoinbase` use a separate `verify_and_broadcast_transactions` path. `external.broadcast` defaults to true, so the disposable outbox wallet should explicitly set it to false and prohibit other callers. A source search found the wallet's actual chain publication calls in that separate path, not the PCZT operations or sync loop. Extraction can queue **transaction status/enhancement queries**; inspected sync code services them with read/status requests, not publication. [Payments](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/payments.rs), [sync](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/sync.rs).

## Extraction storage and the decisive replay hazard

For a PCZT carrying `zcash_client_backend:proposal_info`, `pczt_extract` calls `extract_and_store_transaction_from_pczt`. This reconstructs the transaction and its sent outputs, then calls `store_transactions_to_be_sent`. In the pinned SQLite backend that operation uses `WalletDb::transactionally`: transaction raw data, spent-note links, sent-output metadata, internal received/change notes, and classification writes are committed together. Orchard spend links stop those notes being selected for subsequent proposals. PCZTs lacking the proposal metadata are extracted with `stored=false` and do not provide this protection. [Backend extraction implementation](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_backend/src/data_api/wallet.rs#L3504), [SQLite transaction wrapper](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_sqlite/src/lib.rs#L1869), [store implementation](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_sqlite/src/wallet.rs#L3680).

**Repeating extraction is not a byte-preserving recovery procedure.** `TransactionExtractor::extract` generates binding signatures with `OsRng` on every extraction. Consequently a saved signed shielded PCZT can yield different serialized authorization bytes when re-extracted. The backend stores transactions with `ON CONFLICT (txid) DO UPDATE ... raw = :raw`; sent notes are also upserted, and Orchard spent-note links use `ON CONFLICT ... DO NOTHING`. The source therefore suggests repeated Orchard extraction can update the same transaction record, but does not establish identical-byte replay or prove live repeat support under all wallet/chain states. [Randomized binding signature generation](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/tx_extractor/mod.rs#L101), [raw transaction upsert](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_sqlite/src/wallet.rs#L5271), [spent-note link upsert](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/zcash_client_sqlite/src/wallet/orchard.rs#L676).

A lost extraction response must retain wallet ownership and the saved signed PCZT. Do not rerun creation, discard ownership, infer rollback, or release the wallet on a timeout. After final-byte commitment, extraction is forbidden; only committed bytes may be submitted. Before commitment, an explicit reconciliation procedure needs qualification. A possible future procedure is to derive the intended transaction identity independently and recover the exact already-stored raw transaction with the wallet quiesced. This report does **not** implement or endorse direct database edits or assert that such a procedure is qualified. Zallet's `getrawtransaction` implementation reads the chain view, not the unbroadcast wallet record; `z_viewtransaction` reads wallet data but does not return raw hex. [getrawtransaction](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/get_raw_transaction.rs#L477), [z_viewtransaction](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/view_transaction.rs).

## Caller death, timeout, and restart

The RPC server installs a timeout middleware. Proving and extraction move their expensive work into Tokio blocking tasks; source code does not install a caller-linked cancellation signal for those tasks. Dropping a caller/response future is therefore not evidence the blocking operation stopped. A remote extraction may commit after the application dies. Wallet process death differs: in-progress process work stops, while SQLite recovery governs committed/rolled-back storage. Neither outcome may be inferred from an application marker alone. Actual caller-death/drop observations appear below; arbitrary wallet-process termination remains outside their scope. [RPC server](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/server.rs), [blocking task wrapper](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/task.rs), [extract](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods/pczt_extract.rs#L108).

Creation and extraction RPC entry points additionally call `ensure_synced`; an offline wallet with no synced chain cannot be treated as a faithful substitute for the requested disposable funded chain. [RPC methods](https://github.com/zcash/zallet/blob/e5c16c464d2d641e5a7c386f3682cfa37e1c43f9/zallet-core/src/components/json_rpc/methods.rs#L1516).

## Payment-effects inspection gap

Current `pczt_inspect` returns recipients/values, fee, expiry, branch, policy, proof/signature counts, and signing hints. Its shielded output entries contain only optional `value_zat` and `user_address`. It exposes neither memo bytes nor an authenticated change-ownership classification. Comparing only this JSON with the request is insufficient to verify the approved payment effects, especially memos and change.

The pinned Rust `pczt` crate exposes Orchard recipient/value/rseed/commitment/ciphertext/proprietary fields. On a **clone** of a PCZT, public `Redactor` APIs can attempt memo recovery with `replace_enc_ciphertext_with_decrypted_memo_plaintext(NoteVersion::V2)`; `EncCiphertext::MemoPlaintext(...).to_memo()` yields all 512 bytes after successful recovery. Missing fields or decryption failure leave ciphertext unchanged and must fail closed. The original signed artifact must not be replaced with the inspection clone. Compare the decoded real recipient receiver, not only the optional display address. Internal/change ownership needs independently trusted wallet viewing-key derivation; private backend `postcard` metadata alone is not authenticated evidence. These were the capabilities identified during initial source inspection. The independently tested verifier now covers the bounded real fixture described below. [Public Orchard data](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/orchard.rs#L606), [memo recovery API](https://github.com/zcash/librustzcash/blob/1f6bb2072e7fcb142b0d90ff7b267a8699a84818/pczt/src/roles/redactor/orchard.rs#L225).

## Actual wallet-boundary experiments

The official release binaries ran in the workspace-local Linux VM with four vCPUs and 6144 MiB RAM. The disposable sender was funded before any business PCZT existed, then stopped, configured with `external.broadcast=false`, and restarted. The receiver also had publication disabled. The chain used the regtest genesis and exact activation map in [the stack report](qualification-stack.md): earlier upgrades at height 1, NU5 through NU6.3 at height 2, active branch `37a5165b`. Zebra reports the BIP70 chain label `test` for this regtest, so that label alone is insufficient to select it.

The following are actual wallet-boundary experiments, independently of the Outbox service acceptance scenarios. Their redacted [summary](../integration/evidence/wallet-boundary/summary.json) contains digests and observations. Spending keys, viewing keys, credentials, PCZTs, addresses, and full raw transactions are retained only in protected disposable working state.

This closes the previously identified inspect-only gap for that bounded fixture. It does not extend `pczt_inspect` itself or qualify every possible wallet transaction.

## Corrected service and genuine A/B recovery

A new chain and wallet pair ran all nine scenarios plus genuine identical-intent A/B recovery under the corrected service and actual verifier. The pre-dispatch durable bindings differed by payment/operation/owner while sharing one approved-intent digest. Cross-adoption was rejected before RPC; B's original response recovered under its original owner with zero CREATE replay. Both final transactions passed independent effects/proof/authorization/raw-response checks and were observed mined by the receiver. This new run did not repeat the historical wallet-process restart or reorg experiments. [Corrected report and hashes](corrected-real-stack-acceptance.md), [genuine A/B evidence](../integration/evidence/real-stack-corrected-001/bound-create-recovery/summary.json).

## Recovery limits and remaining release gate

The experiments demonstrate why final raw bytes must be durably committed before publication and why extraction must never run again after that commit. Same transaction ID does not mean same bytes. Response-loss tests retained saved artifacts and exclusive ownership; they did not establish a general automatic reconciliation protocol. The repeat helper rejects a transaction already mined or visible in the node mempool and was not used after the controlled publication.

These results establish the recorded release/backend/regtest profile and caller-death behavior. They do not establish a general lost-extraction recovery policy, arbitrary process termination inside wallet SQLite work, parallel use by unrelated wallet callers, production deployment, or NU7 compatibility. Service scenario outcomes are recorded in the acceptance report. NU7 remains an explicit release gate under the proposal; beta.3 must not be advertised as NU7-qualified. See [compatibility qualification](qualification-compatibility.md).

Operational release additionally requires verified freshness/restore across the business ledger, Outbox and wallet; enforced and verified disabled broadcasting/exclusive construction; NU7; actual expiry/rejection; broader reviewed recovery/error classification; and external review. These are unimplemented/unqualified milestones, not protections established by these historical wallet experiments. [Observable criteria](acceptance-status.md).
